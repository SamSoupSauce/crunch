Refactor the client-side player assignment and session recovery logic for the web game to match a minimal, stateless architecture.

### Requirements:
1. **Stateless Identification:**
   - No user auth, no backend session stores. Players interact as either "Player 1" or "Player 2" targeting a specific `room_code`.
   - The server merely accepts moves signed by a player role against that room's state.

2. **Client-Side Room & Role Memory:**
   - Store active room association in `localStorage` keyed by `room_code` (e.g., `{ roomCode: string, role: "player_1" | "player_2" }`).
   - On page load / room entry:
     - If the player enters a `room_code` they have stored locally as Player 1, re-attach them seamlessly as Player 1.
     - If no role exists in storage and Player 1 is vacant, prompt or assign them to the open slot.
     - If Player 1 is taken and Player 2 is vacant, assign them as Player 2.
     - If both slots are claimed, allow spectator/observer state (or read-only board).

3. **Session Teardown:**
   - On game completion (checkmate, draw, win condition), clean up and delete the local storage key for that `room_code`.
   - No complex forfeit or disconnect handshakes. If a player abandons or closes the tab, the game simply stalls until expired by backend bucket lifecycle (24h deletion) or finished by the other player.

4. **Output:**
   - Provide the clean, minimal vanilla JavaScript functions for:
     - `resolvePlayerRole(roomCode, currentRoomState)`
     - `persistSession(roomCode, role)`
     - `clearSession(roomCode)`
   - Keep error handling bare-bones and dependency-free.
